# pstack under T3 Code

The pstack skills are Cursor's, kept as upstream wrote them. This file maps every Cursor mechanic they name to T3 Code, for the Claude and the Codex provider. Where a skill names a construct below, use the mapping. Everything else in the skills holds as written.

T3 Code's own injected instructions win over this file if they ever disagree. Report the conflict to the user.

## Paths

`<pstack-root>` is the installed plugin directory: the directory that holds `skills/`, `agents/`, and `docs/`. It is two levels above the base directory of any pstack skill you are running. The session-start context names it. On Codex, that context arrives only after the user trusts the pstack hook.

A `poteto-agent` given no path looks for poteto-mode under `~/.claude/plugins/cache/t3-pstack/` (Claude) or `${CODEX_HOME:-$HOME/.codex}/plugins/cache/t3-pstack/` (Codex), not `~/.cursor/plugins/`. It compares the `version` in `.claude-plugin/plugin.json` or `.codex-plugin/plugin.json`. Do not search all of `plugins/`, because other pstack ports install there with higher versions.

The skills cite upstream paths such as `pstack/skills/<x>/...` or `git show origin/main:pstack/skills/<x>/...`. Read `<pstack-root>/skills/<x>/...` instead.

## Starting another skill

A skill that names another one ("the **how** skill", "run `/deslop`", "the **prove-it-works** principle skill", "the control skill") means: read `<pstack-root>/skills/<name>/SKILL.md` in full and follow it. Do not call the Skill tool for a pstack skill. Claude refuses it for every skill upstream marks typed-only. If a project or user skill folder (Locations section) holds a skill of that name, read that copy instead. `reflect` puts its edits to a pstack skill there.

- Principle skills live at `skills/principle-<name>/SKILL.md`.
- `deslop`, `control-ui`, and `control-cli` come from Cursor's team kit and ship in `skills/`.
- The control skill for native mobile ("whatever simulator-driving skill the repo has") is T3's device tools when the session has them, driven as T3's device instructions say. A repo skill for the simulator still gives the build, install, and launch-prep steps. Save evidence screenshots and recordings into the work dir (Worktrees section) with the `agent-device` command that `device_open` returns.
- The control skill for a web UI (`control-ui`) is T3's browser when the current request asks for browser work, such as checking the change in a browser, screenshots, or a video of it. Drive `preview_*` as T3's browser instructions say instead of building a harness. The harness's color scheme emulation is `preview_set_appearance`, and its viewport changes are `preview_resize`. Open the project's dev server with `preview_open` and `target: {kind: "environment-port", port, path}` instead of a `localhost` URL. Save each screenshot with `preview_snapshot` and `save: true`, and copy it and the file that `preview_recording_stop` returns into the work dir. Without such a request, T3 forbids `preview_*` for your own edit, so `control-ui` builds its local harness as written.
- A user who types `/pstack:<name>` (Claude) or `$pstack:<name>` (Codex) starts the skill directly. That path is unchanged.
- A `create-skill` step uses the `skill-creator` skill when the session has it. Otherwise follow `playbooks/authoring-a-skill.md`.

## Subagents

Every subagent a skill spawns is one `delegate_task` call, also on your own provider. T3's advice to prefer native subagent tools does not cover pstack lanes, because a native subagent has no `taskId` for `task_status` or `task_cancel` and no `isolation`. Each lane is a T3 child thread with its own provider, model, and effort, so panels can mix Claude and Codex.

Omit `runtimeMode` on every `delegate_task`, so the child inherits yours. A narrower mode is not a sandbox. `approval-required` and `auto-accept-edits` make the user approve the child's tool calls by hand, which stalls an unattended run.

poteto-mode's kickoff line `Read <path>/worker.md before anything else.` is the first line of every `delegate_task` brief and every `t3_thread_launch` prompt, with `<path>` set to `<pstack-root>/skills/poteto-mode`. A lane on a linked environment (Worktrees section) cannot read this machine's files, so its brief carries worker.md's rules as text in place of that line.

| Cursor construct | Under T3 |
|---|---|
| `Task`, "spawn N in one message" | N `delegate_task` calls in one turn, `mode: "async"`. The brief is self-contained: goal, file pointers, write scope, output path, report shape. A child does not see your conversation. |
| `subagent_type: "poteto-agent"` or `"comment-sicko"` | After the worker line, the brief says "Read `<pstack-root>/agents/<file>.md` in full and act as it." (`poteto-agent.md`, `comment-sicko.md`), then the scope. |
| The `model:` line in `poteto-agent.md`, and `generalPurpose` for an `inherit-parent` or `auto` role | The line holds a Cursor slug. Under T3 the lane's `target` sets its model (Model per role), so the file pins nothing. An `inherit-parent` or `auto` lane omits `target` and keeps the poteto-agent read. Claude Code registers the file as the `pstack:poteto-agent` agent type with that slug as its model, so never spawn that type with the `Agent` tool. |
| `subagent_type: generalPurpose`, agent mode | No agent file. Children load the provider's MCP servers, so `recall` investigators keep their sources. |
| A Cursor Project, its coordinator, a Project worker | The coordinator is the root thread. A Project worker is a `delegate_task` lane like any `Task` subagent. |
| `readonly: true` | The brief says read-only, and the lane reads a frozen SHA (Worktrees section). |
| `run_in_background: true`, waiting on the result | Async is the default. A running task's result carries `next`: its completion wakes you. Continue other work, and end the turn when none is left. Do not poll, and never call `task_status` on a running task before that wake. "The Task response body" is the task `summary`. |
| Resume, message, or queue a follow-up | A new round is a new `delegate_task` with the full consolidated brief and a new `clientRequestId`. Never `t3_thread_send` a new round to `childThreadId`. Send to the child only for upstream's narrow case: state that lives in that child. A live child takes `mode: "queue"` or `"steer"`. A child whose task finished can still take a send, for example when its worktree holds uncommitted changes. When the send returns a `taskId`, record it, and its completion wakes you. A queued or restarted follow-up gets its own task. A steer returns the task of the turn it joins, which you may already track, and none when that turn has no task. To get the child's answer as data, pass a JSON Schema as `outputSchema`. T3 queues that send instead of steering it and has the child return the result with `t3_submit_output`. When the completion wakes you, read `output` with `t3_thread_wait` and the send's `runId`. A run that ended without submitting has no `output`. |
| Stop, hold, cancel nested subagents | `task_cancel` (it stops nested tasks and their PR watches). A hold is a `t3_thread_send` with `mode: "steer"` and the zero-writes order. |
| Liveness, the Cursor dashboard, recorded subagent IDs | Record `taskId` and `childThreadId` where upstream records subagent IDs, including each `taskId` a follow-up send returns. Probe a running child, such as on an audit tick, with `t3_thread_read` on its `childThreadId`: `status`, `updatedAt`, its latest activity, and `pendingRequestCount`. `pendingBackgroundTasks` lists work a child still waits on after its run ended, such as a subagent or a command marked `awaited: true`, and `blockedOnThreadWait` is true while its run only waits on another thread. A task whose `status` is `starting` has a child whose provider has not begun its turn, so no work has started. None of these means the child is stuck. A pending request is a question (Questions section) or an approval, and neither wakes you. You cannot grant an approval. Ask the user to approve or deny it in the child's thread, named by the `link` the task returned. |
| Eval blinding | Also blind the `title` and the worktree path, which the child can see. |

`task_status` only finds tasks your own thread delegated. A grandchild's task belongs to its parent.

A task in a linked environment (Worktrees section) returns `childThreadId: null` and a `remoteChild`. Where this file names `childThreadId`, use `remoteChild.threadId` and pass `remoteChild.environmentId` as `environmentId` to the thread tool.

## Model per role

Upstream reads per-role models from "the `/setup-pstack` rule" (`~/.cursor/rules/pstack-models.mdc`) and falls back to slugs written in the skills. Under T3:

1. Read the role's line in `~/.agents/pstack-models.md` (written by `/setup-pstack`). The line format is `<role>: <descriptor>[, <descriptor>]`, and a descriptor is `<provider>:<model>@<effort>`. Comment Sicko, which `no-comments` spawns, is a judgment lane, so it reads the `judgment and prose` line.
2. Resolve each descriptor against `orchestrator_capabilities` into `target: {providerInstanceId, model, options}`. Call it once, before your first `delegate_task`, and again only after `delegate_task` rejects a target.
   - Provider is a `providerInstanceId` such as `claudeAgent` or `codex`. The short form `claude` means the instance whose `driverKind` is `claudeAgent`. Use an instance with `canRunChildTask: true`.
   - Model is a catalog model id. A short form such as `opus` means the newest catalog id that contains it.
   - Effort goes into the model's effort option (`effort` on Claude, `reasoningEffort` on Codex), and must be one of its `values`. A model without an effort option takes a descriptor with no `@<effort>`, and the target carries no effort option.
   - `orchestrator_capabilities` lists a short set of models per provider and leaves out legacy ones, but `delegate_task` accepts any catalog model id. Send a full model id the list lacks as it is. Call `orchestrator_capabilities` again with `search` set to the model only for a short form the list lacks or after `delegate_task` rejects the model.
   - A project can turn a provider off. `orchestrator_capabilities` still lists it, but `delegate_task` refuses it as "disabled for project".
   - When the search finds nothing or the provider is off, never switch the lane to another model or provider on your own. Name what is missing and ask the user which to use (Questions section). This replaces every fallback a skill gives for a rejected model, such as a family default, the closest valid slug from the error, or the parent model.
   - Compare the `providerInstanceId`, `model`, and `options` that `delegate_task` returns with the target. If they differ, say so in the reply. The provider can still run another model, such as when the user's organization disallows the requested one. A finished task then reports it in `executedModel`, and T3 starts its summary with a note that names both models. Name the model that ran in the reply too.
3. `inherit-parent` or `auto` means: omit `target`. The lane runs on your own provider and model, and it still counts toward a panel's fan-out.
4. With no sheet line, translate the skill's default slug: `claude-opus-5-5-<effort>` or `claude-opus-5-5-<effort>-fast` is `claude:opus@<effort>`, `claude-fable-5-2-<effort>` is `claude:fable@<effort>`, and `gemini-4-neon-<effort>` is `antigravity:gemini-4-neon@<effort>` when the catalog lists an `antigravity` instance that can run child tasks. When that instance lists no Gemini 4 Neon model, it is `antigravity:gemini@<effort>`. Without such an instance it is `codex:gpt-6.1-sol@<effort>`.
5. Families and vendors go by the catalog model id, as the arena skill's Phase A and Phase C define them for slugs. `claude-fable-*` is its own family, apart from the other `claude-*` models, and any other id's family is its text before the first hyphen, so every `gpt-*` model is one family. Fable and the other Claude models are one vendor. A cross-family reviewer runs on a model of another family than the work it judges, and arena's cross-judge on a model of another vendor than yours.
6. "Match the model to the job" moves only the target's effort. Effort steps along `low`, `medium`, `high`, `xhigh`. No role runs above `xhigh`, so never pick `max` or a higher catalog effort such as `ultra` or `ultrathink`. No lane runs in fast mode, so upstream's `-fast` slugs run the same model at standard speed. A lane on your own provider instance and model keeps every option of yours that its target does not name, so when your session runs fast, that lane sets `fastMode: false` or `serviceTier: "default"`. In that case an `inherit-parent` or `auto` lane also names your provider instance and model as its `target`, with the same option, instead of omitting `target`. A lane on another model inherits none of your options. Send it only options its catalog entry lists. A model with no speed option, such as `claude-fable-5-2`, rejects `fastMode`. When `delegate_task` rejects an option, drop it from that call and from every remaining lane of the fan-out before you retry.

## Worktrees and parallel writers

T3 has no cloud agents. Every lane is a `delegate_task` child on this machine or on a linked one. A local child shares the parent's checkout unless the call sets `isolation: "worktree"`.

- **A lane that writes gets its own worktree.** Commit what the lane builds on, then delegate with `isolation: "worktree"`. T3 creates the worktree from your current local commit, runs project setup, and starts the child there. It does not copy uncommitted edits. The child commits its work and reports its branch and head SHA, so the parent reads the result by ref from its own checkout. The worktree belongs to the child's thread, so do not remove it. Without a usable linked environment, this replaces "a cloud agent per worker", `environment: "cloud"`, `cloud_base_branch`, and "each worker its own worktree". Interrogate's adversaries are such lanes, so commit the scope's uncommitted changes in place of copying them into each worktree.
- **A lane on another ref gets a worktree from the parent.** Isolation always starts from your current commit. For a lane on a PR branch, such as a PR owner's fix round, or on another SHA, run `git worktree add [--detach] ${TMPDIR:-/tmp}/pstack/<repo>/<run>/<lane> <ref>` and delegate without `isolation`. The brief names the path, and the child works only there. Keep the worktree until the last step that reads it is done (verification, merge). Then the parent removes it.
- **A before run gets its own worktree too.** Reproduce the old behavior in `git worktree add --detach ${TMPDIR:-/tmp}/pstack/<repo>/<run>/before origin/<default-branch>`, whether the root or a lane runs it. Never copy the default branch's files into the working checkout, because the next commit picks them up.
- **Read-only lanes review a frozen SHA.** Before a round of read-only lanes, such as the `how` subagent or the arena judge, commit what is under review and run `git worktree add --detach ${TMPDIR:-/tmp}/pstack/<repo>/<run>/review-<sha> <sha>`. The brief names that path and the SHA, and the round's read-only lanes read only there, because your own worktree keeps changing while they work. Remove it after you synthesize the round. A read-only lane reads code, diffs, and the evidence a writing lane produced. It does not build or run the app unless its brief asks for that.
- **A Shipping verifier checks the final head.** Start it only after every lane that can move the PR head has returned: a no-comments lane that commits, a fix round, and a trail review whose flags you will act on. A verifier that starts earlier gets cancelled or superseded when the head moves.
- **Evidence outlives worktrees.** Write the decision log, verification output, review prompts, and child reports under `${PSTACK_STORE:-$HOME/.pstack/store}/<repo-name>/<run>/`, never inside a worktree. That directory is show-me-your-work's "work dir". `git worktree remove` deletes ignored files, and `gh pr merge --delete-branch` removes the worktree that holds the merged branch. A project verification skill that writes evidence inside the checkout (`build/`, `work/`) still applies. Copy this run's evidence from it into the work dir before the reply or the trail cites it. Never copy build outputs such as `DerivedData`, `target/`, or `node_modules/`, or evidence from other runs.
- **Cleanup removes only what the root made.** When the user asks to clean up, remove the worktrees the root added with `git worktree add` and its scratch files outside the work dir. Keep each child's worktree, which belongs to the child's thread, and keep the work dir, which holds the evidence the trail and the PR cite.
- **The user picks the root's workspace.** The user starts a thread in a worktree from the T3 UI. The root works in the checkout its thread is in and never moves it. If the root sits on `main` and the task writes, it creates a branch there with `git switch -c <branch>`. Never call `t3_worktree_handoff`. It detaches the provider session, and the queued continuation can wait for minutes or never start.
- **A linked environment stands in for a cloud VM.** `t3_environment_links` lists the user's other machines, when T3's Labs beta for them is on. Run a lane that upstream sends to the cloud on a link whose `status` is `reachable` and whose `access` is `auto` or `full-access`, because a narrower link makes the user approve the child's tool calls by hand. Never call `t3_environment_link` unless the user names a machine to link, because it asks the user to approve the link. Delegate with `target.environmentId`, and resolve the role's model with `orchestrator_capabilities` given that `environmentId`. The task runs in that machine's checkout of the repository and takes no `isolation` or attachments, so only pushed commits reach it. When `delegate_task` finds no project for the repository there, run the lane here. Push the base first. The brief tells the child to fetch it, run `git worktree add ${TMPDIR:-/tmp}/pstack/<repo>/<run>/<lane> <ref>` there, and work only in that worktree. The child pushes its branch, returns its evidence in its report, and then removes the worktree. A lane that needs this machine, such as a control skill run, a simulator, local transcripts, auth that exists only here, or the work dir, stays local. Name each remote lane's machine in the reply.
- **A lane that drives a simulator or emulator gets its own device.** Pick one per lane from your `device_list`, and put its `hostId` and `id` in the brief, as T3's device instructions say, plus its `booted` value. Do this for every lane that may drive a device, such as an interrogate adversary or a Shipping verifier. A lane never creates a simulator for itself, because `device_open` refuses an id that `device_list` does not show, and a new simulator can stay off that list for a minute or more. When a lane needs a new simulator, create it yourself and put it in the brief once `device_list` shows it. Two lanes never share a device, so device lanes beyond the free devices run in sequence. Call `device_close` on a device you opened yourself before you give it to a lane, because your open session locks the lane out. Before it returns, the lane calls `device_close` on its device, with `shutdown: true` when it was not booted, so the next lane can open it and no idle simulator holds CPU. A lane that ends without that call, such as a lane you cancel, can leave its device locked. When a lane reports `DEVICE_IN_USE`, do not wait for the other session. Give the lane a different device, and prefer one that `device_list` shows as not booted.
- **Upstream's capacity numbers assume cloud VMs.** Cap in-flight writing lanes at what this machine and each linked machine you use can run. Give each live lane its own ports and data directories per the project's verification skill. If the app cannot run side by side, run those lanes in sequence. A push that runs a pre-push gate waits while a lane drives the shared VM, simulator, or app.
- **Separate top-level threads** come only from an explicit user request for them. Then use `t3_thread_launch` with a `workspaceStrategy`. A launched thread is not a task: follow it with `t3_thread_read` or `t3_thread_wait`, never `task_status`, and it does not wake you when it ends. `t3_thread_wait` with `untilDelegatedWorkSettled: true` also waits for the tasks that thread delegated, and its `resultRun` names the run that holds the final answer. To get the thread's answer as data, launch it with `message` and an `outputSchema`, then read `output` from `t3_thread_wait` with `untilOutput: true`. `generateTitle: true` has T3 name the thread from `message` the way the app does. `title` is still required.
- **Listing worktrees.** `t3_worktree_status` reports only your own thread. To audit every worktree, use `t3_worktree_list`, `t3_thread_list`, and `t3_thread_read` per thread for its `worktreePath`. `t3_thread_list` with `allProjects: true` lists every project's threads in one call, and each item names its `projectId`. It also returns up to 5 of each thread's open linked PRs in `pullRequests`, watched ones first, the number of its open linked PRs in `openPullRequestCount`, and the number of all its linked PRs in `pullRequestCount`. A thread with `openPullRequestCount` 0 and `pullRequestCount` above 0 has only merged or closed PRs, so its worktree is a cleanup candidate. To name those PRs, call `list_thread_pull_requests` with `threadId` and `states: ["merged", "closed"]`. Add `git worktree list` for detached worktrees, which `t3_worktree_list` omits.

## Pull requests, watching, and loops

**Only the root thread owns a PR in T3.** T3 hides `watch_pull_request` and `unwatch_pull_request` from a delegated child.

- **PR tools.** T3 lists the `pull_request_*` tools, `ci_logs`, and `ci_rerun` when it can reach the thread's forge, to delegated children too. When they are listed, use them, not `gh` or `origin`, wherever a playbook reads, lists, opens, edits, reviews, replies on, closes, or merges a PR, or reads or re-runs its checks. Without them, the playbooks' forge commands apply. `pull_request_update` cannot change a PR's base, so Shipping's retarget to trunk stays on `gh pr edit --base` or `origin pr edit --base`.
- **Shipping verdicts.** A verifier posts its verdict with `pull_request_review` and `verdict: "comment"`. The `body` holds `PASS`, `PASS+NOTES`, or `FAIL` and the head SHA it ran, and each finding with a file and line goes in `comments`. It never sends `approve` or `request-changes`, because T3 agents act as the user's forge account and a verdict is not a forge approval.
- **Landing (Shipping step 4).** Merge with `pull_request_merge`, `method: "squash"`, and `expectedHeadSha` set to the full head SHA the verdict covers, so T3 refuses a head that moved. When the run is layers of a native GitHub stack (`stack.kind` is `native` in `list_thread_pull_requests`), land it with one call on the ceiling with `stack: true`, in place of one merge per PR. T3 pins each lower layer to its current head, not to its verdict, so run step 3's check on every layer first. A derived stack merges one PR at a time. Arm auto-merge with `auto: true` under step 4's rule, never with `stack`. A result `state` of `open` means auto-merge or a merge queue holds the PR. Read each PR back with `pull_request_read`. A landed PR reads `merged` with trunk as `baseBranch`.
- **Babysit threads and CI.** Read review threads with `pull_request_read` and `include: ["threads"]`, and page with `cursor` until `nextCursor` is null. Reply with `pull_request_respond` and the thread's `reviewThreadId`. Set `resolved: true` on a bot's thread once the reply cites the fixing commit or a disproof. Leave escalated threads and human reviewers' threads open. Read a failing check with `ci_logs`, and spend a flake's one fresh build as `ci_rerun` with that `check`.
- **Opening a PR.** `pull_request_create` is the run's PR tool. Call it with `draft: false`, and with `base` for a stacked layer. It pushes the calling thread's branch when the remote lacks commits, opens the PR, and links it to that thread. Without it, create the PR with the resolved forge (`gh` or `origin`), ready for review, never draft. The root links every PR, each stack layer included, with `link_pull_request` for one PR or `link_pull_requests` for several in one call. A child that opens a PR returns its URL and head SHA, and the root links it.
- **Linking issues.** The root links every issue the run works on or files, such as the tracker issue in benny's reproduce automation, with `link_issue`, so T3 shows it beside the thread. A child that works on or files an issue returns its URL, and the root links it.
- **A merged dependency PR can end the run.** T3 settles a thread at a turn end once every PR linked to it has merged. Settling ends the session and kills its background commands, such as a push through a pre-push gate. A run that merges a dependency PR in another repo before it opens its own PR is exposed. Open and link the run's own PR before the dependency PR merges. If the dependency merged first, unlink it before you end a turn that still waits on work. Call `unlink_pull_requests` with `states: ["merged"]`, then `unlink_pull_request` on any merged dependency missing from its `unlinked` list, because the call trusts T3's last known state. Link them again after the run's own PR is linked.
- **Several repositories in one project.** When your prompt carries a `<workspace_folders>` block, the project covers every repository it lists, so a run can change a dependency in another repository from its own thread. Run Git inside the repository you change, and commit in each one separately. `pull_request_create` opens a PR only from the thread's root folder. Open a PR in another listed repository with the resolved forge, run inside that repository, and the root links it with `link_pull_request`.
- **Review guides.** When the root hands PRs to the user for review or merge, it reads each with `read_pull_request_guide`. Then it calls `write_pull_request_guides` once for every PR whose guide is missing or `stale`. A run takes minutes, so do not wait for it. The user reads the guide in the PR's Guide tab. Pass each PR as `repository` and `number`, because the `url` form can fail to find the project's checkout. A PR whose outcome is `failed`, for example because guides are off in T3's Source Control settings, gets no guide. Give its `detail` in the reply and go on.
- **A PR owner (autopilot, multi-phase plans)** is a role, not a long-lived agent. Each owner round (build, fix, merge) is a fresh `delegate_task` in that PR's worktree. The round does its work, reports the PR URL, head SHA, and state, and returns. The root decides and delegates the next round.
- **Babysit inside a child.** A child told to babysit does one `check` pass, fixes what it can, and returns the PR state. It never arms a watch.
- **`/loop` around a PR.** This covers babysit's `drive` mode, shipping, and autonomous-run events. The root calls `watch_pull_request` and ends the turn. T3 wakes it on checks, reviews, and conflicts. Checks that already pass when the watch starts never wake it, so when the result's `checksState` is `passing`, do a wake's steps in the same turn instead of ending it. On each wake, take the verdict from `<pstack-root>/skills/poteto-mode/scripts/watch-pr/watch-pr --status-only --pr <number>`, run in the PR's checkout (or `pull_request_read`, else the playbook's `origin` or `gh pr view` read), act, and keep the watch armed across push waves. Call `unwatch_pull_request` before handing back to the user. `scripts/watch-pr` stays the verdict oracle.
- **`/loop` on a fixed cadence** (`/loop 1h`, audit ticks, heartbeats). The root calls `schedule_task` with `{type: "interval", everyMs: 3600000}` bound to its own thread, reports `nextRunAt`, and calls `delete_scheduled_task` when the run closes. To read that schedule again, such as on session pickup, call `list_scheduled_tasks` with its `scheduledTaskId`. Schedule from the root, because a child's schedule posts into the child's thread.
- **`/loop until X`** with no outside event: keep iterating within the run. Add a schedule only when the work must survive turn ends.
- **Events a PR watch cannot see.** T3 refuses to watch a PR that is already merged or whose host it cannot read, such as when `gh` is missing or signed out, and it cannot watch a ref, a branch without a PR, or a post-merge CI run. On Claude, wait on an event that a command can wait for, such as a post-merge CI run (`gh run watch <run-id> --exit-status`) or a deploy (its CLI's wait command), by running that command as a long shell command (Claude item below). For an event no command waits on (an autonomous run waiting on a ref), on Codex, and for a heartbeat fallback, the root calls `schedule_task` with an interval bound to its own thread. When the event has a known time, such as a release window or a deploy ETA, use `{type: "once", runAt}` with an ISO time and offset instead, so the root wakes once at that time. The prompt states the check and the exit condition. Call `delete_scheduled_task` once the condition holds.
- **Long shell commands on Claude.** Run a long command, such as a gate, a test suite, or a build, with `run_in_background` and end the turn. Its exit wakes you, and so does each delegated task that finishes. Before you end the turn, call `t3_background_wait` with `taskIds: ["<id>"]`, where the id is the one that Claude Code shows when the command starts. It takes shell task ids only. A `delegate_task` task id never matches, and a delegated task wakes you on its own. The result lists each id under `matched` or `unmatched`. An unmatched id marks nothing, so check that it is the id of a command that still runs. The thread then stays in the user's Working list instead of their inbox, T3 does not settle it while the command runs, and a T3 restart that kills the command wakes you with a note. Mark only a command whose result you will act on, never a dev server or a watcher you leave running. Do not wait in a foreground loop while children run, because a child's completion can stay queued until your turn ends. A command you start with `run_in_background` already wakes you when it exits, so do not add a waiter loop for it. Use an `until [ -s x.exit ]` loop, itself run with `run_in_background`, only for an exit file that a process you did not start that way writes. A foreground call stops at 600000 ms whatever its `timeout`. The pstack hook blocks a foreground `until` or `while` loop that sleeps.
- **Long shell commands on Codex.** Never end a turn that waits only on a background shell command. It dies when the user settles the thread or the session ends, and then nothing wakes you. Write the reply first. Report what is still pending as a next step.
- **Stacks.** `list_thread_pull_requests` reports linked PRs, 50 a page, and the whole stack chain of each PR on the page. Pass `nextCursor` back as `cursor` until it is null.

## History and transcripts

- **Current chat.** `t3_thread_read` with your thread id (`view: "activity"` lists tool calls and files read). This replaces `agent-transcripts/` paths and "the chat UUID". `currentThreadId` in a `t3_thread_list` result is your thread id. A child that reads this run's transcript, such as show-me-your-work's cross-model reviewer, gets that thread id and reads it with `t3_thread_read`. Never pass it a JSONL path.
- **Earlier chats** (recall, session pickup, show-me-your-work audits). Use `t3_thread_search` and `t3_thread_list` in this project only. `t3_thread_search` returns title, branch, and PR matches first. A message match needs every query word of three or more characters and carries `source` (`user` or `assistant`), a `snippet`, and `messageCreatedAt`, so pick threads from the snippets before you read them. Message matches fill at most a fifth of `limit`, so pass `limit: 50`, the maximum, when you look for message content. Search skips subagent threads. Drop the match whose `threadId` equals the result's `currentThreadId`, which is your own thread. Pass thread ids to children, not file paths. Page a thread the way the description of `t3_thread_read` in your session says, because the cursor parameters and the order of a read without a cursor differ between T3 builds. Read a long thread in pages of `limit: 20` with `maxCharsPerItem: 2000`, and recover a long item with `itemId` and `textOffset`. T3 ends a page at about 30,000 characters and reports the rest through `hasMore` or `earlierPosition`. On Codex, never print a raw `t3_thread_read` result. Keep it in a variable and print what you need, such as each item's `position`, `type`, and first 300 characters. Cite a thread by the `link` a thread tool returned, verbatim, never by a title or a bare id. With only an id, `t3_thread_read` returns its `link`.
- **Messages from other threads.** A `t3_thread_read` item with `senderThreadId` is a message that thread sent with `t3_thread_send`, such as a parent's follow-up. The user did not type it, so do not read it as the user's words.
- **The issue tracker** (recall's shared record). For the project's own tracker, find issues with `list_issues` and its `query` and `state`, then read each with `read_issue`, which returns the body, recent comments, and linked PRs. `read_issue` also takes the `url` of an issue in a repository that no project here holds, read-only.
- **Shell fallback.** `~/.claude/projects/<encoded-cwd>/*.jsonl` (Claude) and `~/.codex/sessions/**/*.jsonl` (Codex).
- **Pinned and active chats** ("from the user or the sidebar") are the threads `t3_thread_list` returns with `pinned: true` or `settled: false`, called with `includeSubagents: false`. That leaves out child tasks and the tasks a linked environment delegated here, which `delegatedFrom` marks in any list or read. A child task of a pinned or active chat is in use too, and its `parentThreadId` names that chat. Add `allProjects: true` when the work spans repositories, such as a disk cleanup.

- **Project skill** (a generated verification skill or `.cursor/skills/<name>/`, for example). Write `.claude/skills/<name>/` and symlink `.agents/skills/<name>` to it. Claude reads only `.claude/skills`, and Codex reads `.agents/skills`.
- **User skill** (`~/.cursor/skills/<name>/`). Write to `~/.claude/skills/` and `~/.agents/skills/`.
- **`.cursor/rules`.** Read `CLAUDE.md` and `AGENTS.md`, plus any `.cursor/rules` the repo still has.
- **"The root agent's store"** (autopilot-full). Use `${PSTACK_STORE:-$HOME/.pstack/store}/<repo-name>/`. No system prompt names it, so each brief that writes there names the full path. Never write the store inside the checkout.
- **"MCPs from the Cursor environment" and `mcps/`.** Group your tools by MCP server name.

## Questions and the user

- **`AskQuestion`.** On Claude, use `AskUserQuestion`. On Codex, use `request_user_input` only when the session exposes it and allows it in the current mode (Codex limits it to plan mode). Otherwise ask one plain-text question with labeled options.
- **Text the user must read mid-turn.** On Claude, text written before a tool call can reach the user only as a summary. Send what the user must read in full before the turn ends, such as `setup-pstack`'s role table before its confirm question, with `send_to_user`, and do not repeat it in the question or the reply. A child's message lands in the child's thread, so a child puts it in its report instead.
- **A delegated child never asks the user.** It returns `BLOCKED` with the question, and the root asks. A child that asks anyway waits, and `t3_thread_read` on its `childThreadId` shows a nonzero `pendingRequestCount`. Find the question with `t3_pending_request` and `action: "list"`, read it with `action: "read"`, and answer it with `action: "respond"`, each with `threadId` set to the child's `childThreadId`. Answer it yourself when the brief or the run settles it. Otherwise ask the user and pass on the answer. On Claude, keep each option's `preview` in `AskUserQuestion`.
- **Visuals** (charts, tables, mockups, Cursor's `/visualize`). Build a self-contained page as an `.html` file in the work dir (Worktrees section), check it with `html_preview`, then publish it with `html_render` from the root. Pass the file's absolute path as `path` to both, so the page is not retyped. The file is a whole document that starts with `<!doctype html>`. T3 refuses a fragment, such as a file that starts with `<style>`. Only a full-access thread may pass `path`. Any other thread gets a capability error and passes the page as inline `html` instead. A child's render lands in the child's thread. Show verification screenshots the same way, for example a before and after grid, before the reply that cites them. A reader who clicks an image outside a link or button opens it full size in T3's image viewer, so a grid can show screenshots small. Write each image as one complete absolute path, in `src` or as a JavaScript string. T3 does not inline a path the page builds from parts. T3 inlines local images into the page, so the thread keeps them after the worktree is gone. To embed a screenshot, a video, or an audio clip in the reply itself, as `/ketchup` asks, write it as a Markdown image whose target is the file's absolute path. T3 renders all three. Keep that file in the work dir (Worktrees section), so it outlives the worktree. A Mermaid fence in the reply renders as a diagram. A generated image needs an image tool from your provider. T3 has none, so without one draw a diagram or chart instead.
- **Files in the reply.** Link each file the reply cites, such as show-me-your-work's evidence, the decision log, a verification log, or a `file:line` that why or blast-radius asks for, as a Markdown link whose target is the file's absolute path. Put a line number in the label and the target, so the label `http.ts:42` links to `/abs/path/http.ts:42`. T3 opens it in its file viewer. T3 resolves a relative path against the thread's working directory, so a path relative to a package or to another checkout often opens a missing file.
- **Secrets** (a CLI token, an API key, a test account password for a verification run). The root calls `request_secret` and puts the link to the page where the user gets the value, such as the service's token settings, in `url`, not in `reason`. The card shows it as a button. For a shell command, pass `delivery: "file"` and read the returned path inside the command, such as `TOKEN="$(cat <file>)" <cli>`. For up to 8 values from one place, such as a test account's email and password, use one card with `fields`, giving each value a `name` and a `label`, and `secret: false` for a value the card may show, such as the email. Fields always arrive as files, so leave out `value` and `delivery: "secretRef"`. The result's `files` maps each `name` to its path. Never print the value, and keep it out of the work dir, briefs, and commits. A child that needs a secret returns `BLOCKED`. The root requests it and puts the file path, never the value, in the next brief. T3 deletes the file after 24 hours, so a schedule or automation that needs the value later reads it from the user's own configuration, such as benny's `BENNY_SLACK_BOT_TOKEN`.

## Cursor products with no counterpart

- **Custom Mode, Option+Enter.** None. Start a task with `/pstack:poteto-mode` (Claude) or `$pstack:poteto-mode` (Codex). On Claude, T3's composer also offers pstack's skills in its `$` picker when the plugin is enabled in Claude Code, and sends the pick as `/pstack:<name>`.
- **Cursor's built-in `/babysit` and `/autopilot` PR watchers.** Not present. The Babysit playbook is the only PR watcher. The Autopilot playbooks are pstack's own, not this built-in.
- **Plan Mode.** T3 interaction mode `plan`.
- **Automations** (`automations/benny`). A webhook or fixed-time `schedule_task`. Each run handles one event. A run that only reads and replies, such as benny's triage, is created with `bindToCurrentThread: false` and `freshSession: true`: the first run makes the automation's thread in a new worktree, and every later run posts there in a fresh session without earlier runs' context. A run that changes code or opens a PR, such as benny's reproduce automation, takes only `bindToCurrentThread: false`, so each run gets its own thread and a fresh worktree from the default branch. With neither set, a task in the creating thread's own project binds to that thread, and every run continues that conversation. A task for another project then gets a new thread per run. Get webhook signing secrets with `request_secret`. To test an automation, call `run_scheduled_task_now`. When its `lastRunStatus` is `failed`, `lastRunError` says why. Put the trigger's conditions in the webhook schedule's `filters`, so other requests never start a run. For benny, `body.event.channel` equals the source channel. A path segment ending in `[]` checks each element of an array. `{path: "body.issue.labels[].name", op: "equals", value: "<label>"}` matches a GitHub issue that has that label, and `notEquals` matches only when no element has the value. Set `dedupe.replayKey` to the sender's delivery id, `{{body.event_id}}` for Slack or `{{headers.x-github-delivery}}` for GitHub, so a retried delivery does not run twice. When a sender fires bursts about one subject, such as pushes to one PR, set `dedupe.coalesceKey` to that subject. Deliveries with the same key within `coalesceWindowSeconds` (default 120, counted from the first) become one run on the latest payload. Never key it on something distinct events share, such as the channel. When benny's configured tracker is the T3 project's own tracker, T3's issue tools are the issue-tracker adapter of benny's triage: `list_issues` with `query` and `state` to search, `read_issue` to read one issue and its linked PRs, `create_issue`, `comment_on_issue` for the source link and recurrence note, and `set_issue_state` to close an issue the run created. They cannot change an issue's title, body, or labels, or delete it, so a write that needs one of those fails closed as the skill says.
- **Grok Bot** (`/make-bot-ui`). None. The skill ships unchanged but has nothing to wake under T3.
- **A Cursor restart.** T3 keeps threads, delegated tasks, and queues across restarts. Re-read each recorded child with `t3_thread_read`. Read `t3_thread_list`, whose `pullRequests` lists up to 5 open PRs per thread. For a thread whose `openPullRequestCount` is higher, call `list_thread_pull_requests` with `states: ["open"]`. Then reattach by PR and branch.

## Local shell

Upstream's commands assume a Linux cloud VM. Under T3 they run on the user's machine, often macOS with zsh, so check `uname` and `$SHELL` before you write shell.

- macOS has no `timeout`. Bound a command with `perl -e 'alarm shift; exec @ARGV' <seconds> <command>`, which exits 142 on expiry.
- zsh does not split an unquoted `$var` into words. Use `${=var}` or an array.
- zsh expands a word that starts with `=` to a command path. `echo =====` fails with `==== not found` and drops the rest of the line. Quote separators (`echo '====='`), or read each file with its own Read call.
- zsh fails a statement with `no matches found` when an unquoted glob in it matches nothing, such as `grep --include=*.rs` or `cat dir/*.exit`. A `&&` chain stops there. The call can still exit 0, so an empty result may hide the error. Quote the glob (`--include='*.rs'`) or use `rg -g '*.rs'`. On Claude in `bypassPermissions` mode, the pstack hook runs a command that holds an unquoted glob or `=` word with `setopt nonomatch; unsetopt equals` in front, so both behave as in bash. In other modes Claude Code refuses `setopt`, so the hook blocks an unquoted `--option=*glob` and an unquoted run of `=` instead.
